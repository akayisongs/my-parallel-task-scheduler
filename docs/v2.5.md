# v2.5 阶段复盘：两端批量化（Double-Sided Batching）与唤醒配平

> **定位**：在不改变单一全局互斥锁（`std::mutex` + `std::deque<TaskType>`）拓扑的前提下，通过生产端显式 RAII 批量缓冲与消费端整批弹出，验证“消除条件变量等待（`cv_.wait`）与降低锁交接频次”所能达到的物理上限。

---

## 一、 核心结论与验收裁决

### 1. 主决战点（`threads=8, producers=1, n_tasks=262144`）验收表

| 被测臂 | 中位数耗时 | 离散度 spread | 等待数 parks | 相对 v2.4 加速 |
| :--- | ---: | ---: | ---: | ---: |
| `v2.4` | 245.067 ms | 3.7% | 163,438 | 1.00x |
| `v2.4-twin` | 245.988 ms | 2.9% | 158,069 | 1.00x |
| `v2.5` (初版均分) | 16.866 ms | 5.3% | 2,698 | 14.05x |
| `v2.5` (终版贪心) | 11.184 ms | 3.0% | 4,070 | 21.91x |

*注：上表 `v2.5` 初版数据来自 5 点探针实验（对应波次 `v2.4` 为 `237.033 ms`），终版数据来自 22 点全量实验（环境 A/A 噪声底仅 `0.38%`）。*

### 2. 对标“真基线”（`v2.4` 最优线程数 `threads=2`）
* **为什么不以 `245.067 ms` 作为唯一分母**：在 `v2.4` 中，将工作线程数从 `8` 降至 `2` 即可在不改一行代码的情况下获得 `24.283 ms`（`v2.4-twin`）/ `24.777 ms`（`v2.4`）的最优基线成绩。
* **真基线击穿幅度**：`v2.5` 终版在 `threads=8` 下达到 `11.184 ms`，比 `v2.4` 的 2 线程真基线（`24.283 ms`）快 **2.17x**；在 `threads=2` 下达到 `8.471 ms`，比真基线快 **2.87x**，显著跨越 `1.5x` 验收门槛与环境噪声底。

## 二、 假说裁决记录（H1 – H4）

### 1. H2（等待代价）：证实，单次 `cv_.wait` 往返均摊成本约 `1.4 us`
* **方法**：在 `v2.4` 中植入 `park_count_`（统计进入 `cv_.wait` 等待循环的次数，即内核挂起次数的上界）。
* **证据**：固定 `n_tasks=262144, producers=1`，当线程数从 `4` 增至 `8` 再增至 `16` 时，等待率（`parks / n_tasks`）从 `4.8%` 升至 `59.7%` 再升至 `83.4%`，单任务成本从 `0.167 us` 线性升至 `0.918 us` 和 `1.232 us`。两点线性拟合斜率约为 `1.37 ~ 1.52 us/park`，外推预测 `threads=16` 的误差小于 `4%`。
* **机理**：业务负载（`1024x1024` 双精度乘加）单任务纯计算仅需约 `3.6 ns`，而一次条件变量等待-唤醒往返代价高达 `~1.4 us`（相差约 390 倍）。消费者总吞吐超过单生产者逐个加锁投递速率时，队列频繁抽空，调度器把 99% 的时间烧在了等待与唤醒上。

### 2. H3（最大队列深度 `max_depth_`）：证伪，指标受启动瞬态污染
* **现象**：在 `n_tasks=64` 的所有线程组中，`max_depth_` 恒为 `64`；在 `n_tasks=262144, threads=8` 下，`max_depth_` 仍高达 `500 ~ 2046`。
* **归因**：主线程在工作线程尚未完成 OS 线程创建与首次抢锁前的几百微秒启动窗口内，已将数百乃至上万个任务灌入队列。`max_depth_` 记录的是启动瞬态水位上界，不能反映运行稳态。
* **修正**：`v2.5` 新增 `steady_max_depth_`（跳过前 10% 即 `tasks_taken_ > 26214` 后的最大深度），实测 `threads=8` 稳态深度仅为 `320`（约 5 个批次）。

### 3. H1（多生产者扩展）：在 `v2.4` 中证实生产受限，在 `v2.5` 中证实提交瓶颈已消除

| 生产者数 prd | v2.4 (ms) | v2.4-twin (ms) | v2.5 (ms) | v2.5 parks |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 245.067 | 245.988 | 11.184 | 4,070 |
| 2 | 115.799 | 116.485 | 11.619 | 3,659 |
| 3 | 101.004 | 104.915 | 11.574 | 2,733 |
| 4 | 93.038 | 90.513 | 13.000 | 1,915 |

* **判读**：`v2.4` 在 `producers=4` 时提速 `2.63x`（`245.07 ms -> 93.04 ms`），证明单生产者单次入队喂不饱 8 个消费者；而 `v2.5` 的 `T(1)/T_min = 1.00x`（`11.18 ms -> 13.00 ms`），证明批量化后单生产者已能完全喂饱队列，继续增加生产者只会增加全局锁争用。

### 4. H4（消费端均分切碎效应）：由 `acq / avg_take` 探针证实并修复
* **问题暴露**：`v2.5` 初版采用 `share = ceil(avail / threads)` 均分出队，配合 `enqueue_bulk` 中的 `notify_all()`。当生产端每次刷入 `64` 个任务并唤醒全部线程时，8 个消费者将一批任务切碎分食。
* **探针实证与修复前后对比（`n_tasks=262144, producers=1`）**：

| 线程数 thr | 均分版 (ms) | 均分 acq/avg | 贪心版 (ms) | 贪心 acq/avg |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 7.318 | 4,096 / 64.0 | 7.985 | 4,096 / 64.0 |
| 2 | 11.215 | 4,886 / 53.7 | 6.905 | 4,096 / 64.0 |
| 4 | 10.101 | 8,374 / 31.3 | 9.392 | 4,096 / 64.0 |
| 8 | 16.866 | 33,637 / 7.8 | 11.037 | 4,096 / 64.0 |
| 16 | 88.743 | 131,155 / 2.0 | 10.859 | 4,096 / 64.0 |

* **修复机制**：将消费端改为贪心整批提取 `take = min(64, tasks_.size())`，并将生产端唤醒改为按批次数匹配 `notify_one()`。改动后从 `t=1` 到 `t=16`，消费者抢锁次数全部收敛至理论极值 `4,096` 次（`avg_take = 64.0`），`threads=16` 的超订惊群退化（`88.743 ms -> 10.859 ms`）被彻底根除。

## 四、 `v2.5` 的物理天花板与下一阶段边界

### 1. 为什么 `v2.5` 卡在 `8 ~ 11 ms` 无法继续逼近 `1 ms`？
* **锁内 `O(n)` 单任务搬移成本**：尽管加锁频次已降至 `4,096` 次，但底层容器仍是 `std::deque<TaskType>`。在 MSVC STL 中，由于 `sizeof(TaskType) == 64 > 8`，`std::deque` 每个元素的块大小退化为 `1`。生产者 `enqueue_bulk` 与消费者弹出过程仍在持有 `queue_mutex_` 的临界区内执行了 `262,144` 次 64B 对象移动及单元素堆内存分配/释放，锁内串行搬运下限约为 `7 ~ 8 ms`。
* **贪心出队的适用边界**：`take = min(64, tasks_.size())` 假设任务同质且细粒度。若面对少量重负载变长任务，贪心出队会导致负载不均（届时需设下限阈值或采用工作窃取）。

### 2. 后续演进方向
* **方向 A（`v2.6` 容器粒度升级）**：将全局队列改为 `std::deque<std::vector<TaskType>>`，生产端与消费端在锁内直接通过 `std::move` 交换 `vector` 的 24 字节控制块指针（锁内复杂度从 `O(B)` 降至 `O(1)`，锁内堆分配归零），验证耗时能否从 `11.18 ms` 进一步压入 `3 ~ 5 ms`。
* **方向 B（`v3.0` Per-Thread Queue + Work-Stealing）**：引入嵌套分治负载（如递归快速排序 / 分治矩阵乘法，工作线程自身也是生产者），测试单一全局锁在线程自产自销场景下的争用退化，并验证本地双端队列 + 工作窃取的正扩展能力。

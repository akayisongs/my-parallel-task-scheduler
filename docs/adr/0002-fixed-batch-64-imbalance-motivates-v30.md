# ADR-0002：固定批大小 64 的负载不均实证与 v3.0 Work-Stealing 演进动机

- **状态**：已采纳
- **日期**：2026-11-24
- **关联文档**：`docs/v2.5.md`、`data/benchmark_summary_wide.csv`、`gemm_benchmark.cpp`

## 背景

`v2.5` 采用生产端固定批上限 `kProducerBatchLimit = 64` 与消费端贪心出队 `min(64, tasks_.size())` 配平 `notify_one()`，在超细粒度微任务（`n_tasks = 262,144`）上取得了显著加速。但 `/deepen` 普查（候选 `C8`）结合实测数据暴露了固定批大小在粗粒度与少量任务上的结构性失效：

- 在 `data/benchmark_summary_wide.csv`（`threads = 8, producers = 1`）：
  - `n_tasks = 64` 时，`v2.5_acq = 1`、`v2.5_avg_take = 64.0`——**8 个工作线程中仅 1 个线程领走全部 64 个任务**，其余 7 核空转，`v2.5` 反较 `v2.4` 退化（`docs/v2.5.md` 记录该点加速比为 `0.71x`）；
  - `n_tasks = 256` 时，`v2.5_acq = 4`，仅切出 4 个批次，仍有半数线程无法参与执行。
- 若将 `gemm_benchmark.cpp` 中 64 个重负载矩阵乘任务（每任务约 4.2 ms）通过默认 `make_batch()` 投递，将整体退化为单核串行执行。
- 面对变长/异构耗时任务或计算图 DAG 子任务动态派发，静态消费批上限无法在运行时重新切分已被单个线程锁定的批次。

## 决策

1. **不在单锁架构中引入自适应批大小启发式**（不在 `v2.5` 上实现动态批策略）。
2. 将“固定批大小 64 无法兼顾粗粒度/变长任务负载均衡与极细粒度吞吐”正式确立为演进至 **`v3.0` Work-Stealing 调度拓扑**的核心架构动机之一：
   - 本地 LIFO 弹出保持缓存局部性与低同步开销；
   - 空闲工作线程跨队列从另一端窃取（FIFO）并在运行时动态再平衡重任务与长尾负载；
   - 通过 `alignas(64)` 隔离每线程双端队列元数据，消除跨核伪共享（False Sharing），并用 Linux `perf`（`cache-misses`、`context-switches`、`cycles`、`instructions`）验证物理收益。

## 后果与约束

- `v2.5` 的 `Batch` 仅作为“同质极细粒度批提交”的对照基线保留，不承担通用全粒度均衡职责。
- `v3.0` 的验收基准除微任务吞吐外，需覆盖粗/变长负载或 DAG 嵌套派发场景，验证多核负载均衡与窃取效率。
